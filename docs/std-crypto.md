# Crypto building blocks: hashes, HMAC, Base64, random bytes

Status: implemented (WEB-CRYPTO), for the web framework
([web.md](web.md)): signed session cookies, CSRF tokens, the WebSocket
handshake. All of it is ordinary Kush in std except the random source, which
is one `kush_sys_*` host call. Tests: `crates/kush/tests/std_crypto.rs`
(known-answer vectors on both backends, balanced allocations).

```kush
use std.sha256;
use std.hmac;
use std.base64;
use std.random;

let digest = sha256.digest(&data);                    // 32 bytes
let tag = hmac.sign(&key, &message);                  // HMAC-SHA256
if hmac.verify(&key, &message, &received) { .. }      // constant time
let cookie = base64.encode_url(&tag);                 // no padding
let token = random.bytes(32)?;                        // from the kernel
```

| Module | Functions | Notes |
| --- | --- | --- |
| [`std.sha256`](../crates/kush/std/sha256.kush) | `digest`, `new`, `update`, `finish` | FIPS 180-4. `update` consumes and returns the `Hasher`. |
| [`std.sha1`](../crates/kush/std/sha1.kush) | same | Broken for collisions; only for protocols that require it (RFC 6455). |
| [`std.hmac`](../crates/kush/std/hmac.kush) | `sign`, `verify` | HMAC-SHA256 (RFC 2104). Keys over 64 bytes are hashed first. |
| [`std.ct`](../crates/kush/std/ct.kush) | `equal` | Comparison whose time depends only on the lengths. |
| [`std.base64`](../crates/kush/std/base64.kush) | `encode`, `encode_url`, `decode`, `decode_url` | RFC 4648; decoding returns `Option<Bytes>`. |
| [`std.random`](../crates/kush/std/random.kush) | `bytes` | `getrandom(2)`; `Result<Bytes, i64>` with errno. |

## Proofs

Every bounds, shift and overflow check in these modules is proved: the
proof report of a program that uses all of them
(`KUSH_PROOF_REPORT=verbose kush check benchmarks/crypto/hash.kush`) lists
no unproved check inside `std.sha256`, `std.sha1`, `std.hmac`, `std.ct` or
`std.base64`. In particular:

- `sha256`'s and `sha1`'s `compress`, `ct.equal`, and base64's `symbol` and
  `value` have empty effect rows: the checker has proved they cannot panic.
  The remaining `panic` in the public functions comes from `Bytes.push`,
  whose byte-range check is a builtin.
- Byte reads are `Bytes.at`, proved in bounds by erased preconditions such
  as `{ 0 <= at && at + 64 <= n && n == Bytes.len(data) }`. The length is
  passed as an `i64` local of the caller: a length term has no upper bound
  for the prover, so `at + 4` could not be shown not to overflow without it.
- Shifts are proved by SHIFT-ELIDE ([runtime-indices.md](runtime-indices.md)),
  added for this work: before it, every shift kept a run-time check of its
  amount, even `x >> 3`.
- Base64 avoids `/` and `%`, which the prover does not discharge: `n & 3`
  for `n % 4`, and buffer sizes that over-estimate instead of dividing.

## Speed

64 MiB on the second PC (`benchmarks/crypto/hash.kush`, 2026-11-14):

| | first version, Cranelift | Cranelift | LLVM `--release` |
| --- | --- | --- | --- |
| SHA-256 | 3355 ms | 514 ms | 240 ms (about 280 MB/s) |
| SHA-1 | 2624 ms | 220 ms | 85 ms (about 790 MB/s) |
| HMAC-SHA256 of 64 bytes | 17.8 µs | 4.3 µs | 1.7 µs |
| Base64 encode / decode | | 374 / 414 ms | 122 / 104 ms |

With the CPU's SHA instructions (SHA-NI-STD, 2026-11-14), on the same
machine; `KUSH_CPU_DISABLE=sha` gives the portable column:

| | SHA instructions, LLVM | portable, LLVM | SHA instructions, Cranelift | portable, Cranelift |
| --- | --- | --- | --- | --- |
| SHA-256 | 76 ms (about 880 MB/s) | 251 ms | 394 ms | 538 ms |
| SHA-1 | 84 ms | 116 ms | 189 ms | 230 ms |
| HMAC-SHA256 of 64 bytes | 0.94 µs | 1.92 µs | 3.9 µs | 4.4 µs |

`update` asks `cpu.sha()` once and runs `compress_ni` (Intel's SHA-NI
sequence through `std.x86`, generated by `scripts/gen-sha-rounds.py`) or the
proved portable `compress` for each block; both have empty effect rows and
proved loads. The accelerated path avoids byte shuffles (big-endian loads
by shifts, lane moves by word shifts), because the x86-64 baseline has no
SSSE3 and Cranelift would call a software `pshufb` for each. Cranelift
still calls a runtime routine per SHA instruction (docs/simd.md); LLVM gets
within about 2.5x of OpenSSL's 30 ms. Tests compare both paths, natively and
in the evaluator (`sha_instructions_and_portable_code_give_the_same_digests`).

For comparison, OpenSSL hashes the same buffer in about 30 ms with SHA
instructions. The portable gains came from:

- **No allocation per block.** The first version built the round-constant
  vector and a 64-word message schedule for every block; now the state is a
  tuple, the schedule a ring of sixteen locals, and the constants literals.
- **Fully unrolled rounds** (generated by `scripts/gen-sha-rounds.py`), in
  the classic in-place form: each round updates two variables and the next
  uses them in rotated roles, so no round copies a local or calls a function
  (Cranelift does not inline). While writing it, 16 unrolled rounds inside
  a `while` took over a minute to check: the loop pre-pass was cubic in the
  body's length. CHECK-LOOP-PERF fixed that (the same loop now checks in
  0.09 s); the code stays fully unrolled because that is the fastest form.
- **Proved checks** instead of run-time ones, for reads and shifts.
- **Base64 by groups** of four characters, with one sign test for a group.

## Choices

- **Wrapping arithmetic is explicit.** Kush integers are checked, so SHA
  additions use `Int.wrapping_add`. Rotations are two `u32` shifts by
  constants: a left shift drops high bits by definition, and its only check
  (the amount) is proved, so no overflow check is turned off.
- **Canonical Base64.** Decoding rejects characters outside the alphabet,
  missing or misplaced `=` (standard form), any `=` (URL form), an
  impossible length, and nonzero unused bits in the last character. Each
  byte string has exactly one accepted encoding, so decoded tokens can be
  compared or used as keys.
- **`hmac.sign`, not `hmac.sha256`.** The module imports `std.sha256`, and a
  function of the same name would shadow it. HMAC here is always SHA-256.
- **Random bytes only from the kernel.** There is no seeded generator in
  std; anything security-related must come from `random.bytes`. The native
  stub retries short reads and `EINTR`; the reference evaluator reads
  `/dev/urandom`. Like `kush_sys_read`, the call fills the buffer's spare
  capacity and frees the buffer on failure.

## Limits

- **Constant time is best effort.** `ct.equal` has no early exit and no
  branch on the data, but neither Cranelift nor LLVM is told to keep it that
  way; this is the usual guarantee of portable code, not a statement about
  the machine code.
- **SHA instructions only through `std.x86`.** They are used when the CPU
  has them; the evaluator runs their Kush specification.
- **No AES, no signatures, no key exchange.** TLS is handled by rustls
  through `kush bindgen` (WEB-TLS), not by Kush code.
