# Project workflow, tests, formatting, and editor support

This document covers the practical project layer that sits on top of the
existing single-file compiler. The language/compiler completion backlog remains
on hold; this milestone is about using Kush for real local projects without
changing the existing language semantics.

Implemented:

- a documented `Kush.toml` manifest with an entry point, package metadata, and
  local path dependencies;
- deterministic local dependency resolution, including cycle, missing-path,
  name-collision, and malformed-manifest diagnostics;
- a generated `Kush.lock` that pins the resolved local package graph;
- `kush new`, project `check`/`build`/`run`/`test`, and a conservative
  formatter;
- `#[test]` functions with per-test processes, readable source diagnostics,
  filtering, listing, captured output, and exit status;
- process-argument forwarding after `--`;
- syntax highlighting for editors, validated `[native]` manifest fields, and
  `kush bindgen` for declarative Rust/C adapters.

Not implemented yet:

- a language server, live editor diagnostics, or go-to-definition;
- package registries, remote dependencies, workspaces, or publish commands;
- incremental compilation or a build cache;
- callbacks, arbitrary Rust ABI, borrowed foreign results, or structs/variadics
  through the native bridge (see [native-interop.md](native-interop.md));


Single-file commands keep their previous syntax and behavior.

## Manifest

`kush new hello` creates:

```text
hello/
  Kush.toml
  src/main.kush
  tests/main.kush
  .gitignore
  README.md
```

A complete manifest looks like:

```toml
[package]
name = "hello"
version = "0.1.0"          # optional; defaults to "0.1.0"
entry = "src/main.kush"    # optional; defaults to src/main.kush
test = "tests/main.kush"   # optional; defaults to tests/main.kush when present

[dependencies]
words = { path = "deps/words" }

# Native libraries and Rust staticlib adapters, linked by build/run/test.

[native]
libraries = ["m"]
library-paths = ["native/lib"]
cargo-manifests = ["adapters/bridge/Cargo.toml"]
```

Rules enforced by the manifest loader:

- `package.name` must be one ASCII identifier (`hello`, `hello_world`).
  `std` is reserved. Dependency keys must be identifiers and must match the
  dependency package's own name; renames are not supported.
- `entry` and `test` are manifest-relative files inside the package. Absolute
  paths and `..` are rejected for entry/test/native paths.
- A dependency `path` is a manifest-relative directory and may use `..` to reach
  a sibling package. The directory must contain its own `Kush.toml`.
- Unknown tables and fields are errors. Unknown manifest fields are not silently
  ignored.
- Dependency graphs are limited to 256 packages and 64 levels. Cycles, two
  different directories claiming the same package name, and a dependency with
  the same name as the root package are rejected.
- `[native]` library paths must be existing directories, and adapter Cargo
  manifests must be existing files. `libraries` entries are bare library names or package-relative archive/shared
  library paths. Absolute paths and parent traversal are rejected.

## Module layout and imports

The project loader builds a deterministic module index and hands it to the
existing `program::load` loader. Source imports are not rewritten.

For a package named `hello`:

| File | Module declaration |
| --- | --- |
| `src/main.kush` (the entry) | `module hello;` |
| `src/util.kush` | `module hello.util;` |
| `src/parser/expr.kush` | `module hello.parser.expr;` |
| `tests/main.kush` | `module hello.tests.main;` |
| dependency `words` entry `src/lib.kush` | `module words;` |
| dependency `words` `src/plural.kush` | `module words.plural;` |

The root project imports its own modules with `use hello.util;`, and dependency
packages with `use words;` or `use words.plural;`. The entry file is registered
as the package root module, so it is not also available as `hello.main`.

Files under `src/` and `tests/` are indexed. File and directory names must be
ASCII identifiers so a module path can be derived without ambiguity. Symlinked
directories are not followed, hidden directories and `target/` are skipped, and
dependency package roots are excluded from the root package's index.

## Lockfile and reproducibility

Project commands resolve the local dependency graph in sorted order and write
`Kush.lock` next to `Kush.toml`:

```toml
# This file is generated by kush. Do not edit it manually.
# It records the resolved local dependency graph.

version = 1

[[package]]
name = "words"
version = "0.1.0"
path = "deps/words"
entry = "deps/words/src/lib.kush"
dependencies = []
```

The file is byte-for-byte deterministic for the same graph. `--locked` is
available on project `check`, `build`, `run`, and `test`. It fails when the lock
is missing or differs from the current resolution; run the command without
`--locked` to update the lock. Local dependencies are not content-addressed:
the lock pins paths, versions, entries, and direct dependency edges, not file
hashes or registry metadata.

## Commands

Run project commands from the project directory or any descendant; the CLI
searches upward for `Kush.toml`. `--manifest-path <Kush.toml>` selects another
project explicitly. Paths with spaces are passed as normal process arguments;
no command uses a shell.

```sh
kush new <directory> [--name <name>]
kush check [--manifest-path <Kush.toml>] [--locked]
kush build [--manifest-path <Kush.toml>] [-o <executable>] [--stats] [--locked]
kush run [--manifest-path <Kush.toml>] [--stats] [--locked] [-- <program args>...]
kush test [--manifest-path <Kush.toml>] [FILTER] [--exact] [--list] [--nocapture] [--locked]
kush fmt [--check] [--manifest-path <Kush.toml>] [FILE...]
```

`kush build` writes `target/kush/<package>` by default. `kush run` builds the
same artifact and then executes it with inherited standard streams. `--stats`
keeps its previous meaning: one allocation-stats line on stderr, unchanged
program stdout and exit status.

Project `check` checks the entry program and, when a test target is configured,
compiles the synthesized test entry as well. It reuses the existing checker; it
does not implement new language semantics.

### Program arguments

Everything after `--` is forwarded unchanged as process arguments:

```sh
kush run -- first "two words" --flag
```

Native programs expose arguments and environment through the `ENV` host APIs.
`ENV.arg_count` includes argv[0]; application arguments begin at index 1.
Single-file `kush eval file.kush -- args...` supplies equivalent program
arguments plus the current process environment to an explicit `Host` context.
Embedding APIs retain their deterministic empty-host defaults unless a host is
supplied. See [host-api.md](host-api.md).

## Tests

A test target is a normal Kush file configured by `[package] test = "..."` or
the default `tests/main.kush`. Declare tests with the `#[test]` attribute:

```rust
module hello.tests.main;

use std.test;
use hello.util;

#[test]
fn addition_works() -> Unit ! {panic} {
    test.is_true(1 + 1 == 2);
}

#[test]
fn helper_works() -> Unit ! {panic, io} {
    test.equal_i64(util.double(21), 42);
}
```

Rules:

- `#[test]` functions must have no parameters, no generics/lifetimes, and return
  `Unit`. They may use any of the four current effects; the generated test entry
  declares `{io, alloc, panic, suspend}`.
- Imported modules can define helper functions, but only `#[test]` functions in
  the test target file are discovered.
- A test target must not define `main`; `kush test` generates one for each test
  process.
- The test target file's module declaration must match the project module index
  (for `tests/main.kush`, that is `<package>.tests.main`).

`std.test` provides:

- `test.is_true(condition)` and `test.is_false(condition)` — panic on failure;
- `test.equal_i64(actual, expected)` — prints both values before panicking so a
  failure report shows useful numbers;
- `test.fail()` — deliberate failure.

Each selected test is checked, built, and run in its own process. That means a
panic or native abort is isolated and reported against the test, while compile
errors point at the original test source with the usual file/line/caret
diagnostic. The runner reports passed/failed counts and exits 0 only when every
selected test passes; a test compile error or failed test exits 1.

```text
running 2 tests in /path/tests/main.kush

test addition_works ... ok
test helper_works ... ok
test result: ok. 2 passed; 0 failed; 0 filtered out
```

Filtering is a substring match on the function name; `--exact` requires an exact
name. `--list` prints names without compiling. Failed test output is shown after
the test lines; `--nocapture` also shows captured output for passing tests.

## Formatter

`kush fmt` is intentionally conservative. The AST does not retain comments, so a
full AST pretty-printer would delete them. Instead the formatter:

- removes trailing spaces and tabs outside string literals, character literals,
  and block comments;
- ensures a final newline;
- preserves comments, string/char contents, indentation, tokens, and line
  endings.

Before writing, it lexes the original and candidate and refuses the rewrite if
the token kinds differ. Lexically invalid files are not rewritten.
`kush fmt --check` writes nothing and exits 1 when a file would change. With no
file arguments it formats all root-package `.kush` files, excluding `target/`,
hidden directories, and dependency package roots.

It is a whitespace hygiene pass, not a code-style reflow tool.

## Editor support

`editors/vscode-kush` contains a grammar-only VS Code extension:

- `.kush` language registration;
- TextMate syntax highlighting for keywords, types, attributes, strings,
  comments, lifetimes, numbers, functions, and module paths;
- bracket/comment configuration.

It does **not** provide an LSP server, live diagnostics, completion, or
go-to-definition. Editor users should run `kush check` or `kush test` for
compiler diagnostics. This is basic syntax support, not full editor tooling.

## Native bridge extension points

Project builds and tests accept native libraries and Rust staticlib adapter
crates through these manifest fields:

- `[native] libraries` — opaque library names/paths for the adapter's link step;
- `[native] library-paths` — validated search directories;
- `[native] cargo-manifests` — validated Cargo manifests for generated Rust
  adapters.

The native builder now consumes these inputs for project build/run/test, using
`native::build_with_options`. Cargo manifests build Rust `staticlib` adapters;
archives and search paths are linked without a shell. Dependencies' native
inputs are included too. Adapter builds use their own target directories and
are performed once per project test invocation, not once per test function.
Cargo resolves Rust dependencies according to each adapter's Cargo manifest and
lockfile; `CARGO_NET_OFFLINE=true` can enforce offline builds. Kush.lock records
the Kush path dependency graph, not a replacement for Cargo.lock.
`kush check` checks types without invoking Cargo or linking. Generated adapters
are declared in a strict `Bridge.toml` and produced with
`kush bindgen Bridge.toml [--check]`, which writes both the Rust shims and the
matching Kush module. See
[native-interop.md](native-interop.md) for the schema, ABI, panic/cleanup
contracts, and trusted-foreign-code limits.

## Verification

The standalone example project is
[`examples/project-demo`](../examples/project-demo):

```sh
cd examples/project-demo
kush check
kush run      # prints 106 and 42
kush test     # runs local-module, dependency, and assertion tests
kush fmt --check
```

The integration suite `crates/kush/tests/project.rs` covers generated projects,
local dependencies, deterministic lockfiles, invalid/missing/cyclic dependency
diagnostics, name collisions, filtering and failure exit status, source
diagnostics, comment/string-preserving formatting, paths with spaces, nested
directory discovery, single-file command compatibility, argument forwarding,
and native adapter linking.

## Project validation and source boundaries

Package, dependency, and module components must be lexical identifiers, not
reserved language keywords. Entry files must declare `module <package>;`.
Explicit test targets outside `src/` and `tests/` are indexed relative to the
package root, for example `check_me.kush` declares `module app.check_me;`.
Source entries and source-tree roots through symlinks are rejected, keeping
build and formatter behavior consistent; path dependency directories themselves
are resolved canonically as before.

Normal test runs check the full test target even when a filter matches nothing.
`--list` remains a parse/discovery-only operation. Test executables are stored
under `target/kush/.tests`, separate from any legal package executable name.
Lockfile read failures are reported as read errors; only a missing file is
reported as missing.
